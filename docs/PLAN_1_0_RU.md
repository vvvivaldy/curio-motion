# Curio Motion: план до 1.0

Состояние на 1 ноября 2026. Отправная точка — опубликованная [0.2.0-beta.1](https://github.com/vvvivaldy/curio-motion/releases/tag/v0.2.0-beta.1), merge 968cde12. Первоначальный план сохранён ниже; пакеты 1–4 завершены, этап 5 готовит локальный 1.0.0-rc.1. [Текущий RC и приёмка](RC_1_0_0_RU.md). План подготовлен локально, публикация 1.0 в эту задачу не входит.

## Принятый объём

План фиксируется по результатам и критериям приёмки, без оценки времени. Переход к следующему этапу — после закрытия обязательных задач текущего. [Состояние этапа 1: шесть задач](STAGE_1_RU.md).

Для 1.0 берём существующий формат редактируемого TypeScript source-project: Pixi/Remotion, локальные примеры, scaffold, записанный звук, официальный MP4 и инструкции пользователя/агентов. По уточнению владельца на этапе 4 официальный объём — только явно записанная macOS arm64/Chrome среда. Linux/Windows текущего кандидата не проверяем; прежний Linux CI — историческое доказательство, конфигурация CI — будущая возможность, а не PASS текущего кандидата. Границу Node для 1.0 утверждаем в пакете 1: у беты engines≥22.12. Проверяем минимальную заявленную версию и выбранную актуальную поддерживаемую ветку; при пересмотре минимума объясняем переход. Конкретную рекомендованную поддерживаемую версию подтверждаем перед проверками, не выбираем по памяти.

Все Windows/Linux маршруты (установка, сборка, browser/export), npm-пакет, глобальный CLI, универсальный риг, автоматическая анатомия, новый язык сцен, облачный рендер, новые стили и фиксированное количество звуков не являются условиями этого 1.0. Дополнительные платформы включаем только с собственной средой и реальной проверкой.

**Обещание 1.0:** новый автор по документированному маршруту может сделать/изменить сцену и получить корректный экспорт в поддерживаемой среде; названные стабильные контракты имеют ясные правила совместимости. Качество постановки, рисунка и звучания проверяется отдельно.

## Что уже есть и не нужно делать заново ради номера

- Принятые сцены переноса/стула/бега/поворотов, короткий сюжет, енот-курьер и инфографика; общие геометрические механизмы уже применялись разными авторами.
- Независимый автор без чата сделал персонажа и инфографику. Другой чистый испытатель установил архив, изменил оба примера, создал blank scaffold и экспортировал два полных MP4.
- Типы, численные/authoring/distribution проверки и сборка проходили; GitHub CI беты зелёный. Базовый порт-прогон 24 сцен/1867 сравнений и отдельные CatV3/BlackCat46/151 прошли. Настроены 25 сцен/1920 сравнений; полный новый прогон именно всех 25 при подготовке беты не заявлялся.
- Полные регрессионные экспорты и сохранённые фильмы имеют доказательства идентичности для своих версий. Последующая очистка source HTML проверена отдельно и не меняла входы рендера.
- Звуки/происхождение/права и инструкции пользователя/автора/критика собраны. Страницы источников очищены от встроенных map-service токенов, общие/вложенные checksum проверены. Эта очистка была ручной — повторяемый выпуск ещё предстоит закрепить.

Эти результаты сохраняем как baseline. Они не заменяют проверку будущего RC после изменений.

Пакеты 1→2 выявляют конкретные проблемы; исправления пакета 3 можно делать по мере их появления. Размер плана определяется полезным результатом и открытыми блокерами.

### Пакет 1: конкретные решения

- Кандидаты на стабильное ядро: контракт сцены/настроек, чистая оценка кадра и времени, lifecycle stage, выбранные документированные координатные/контактные функции. Окончательный перечень выводим из кода и реального использования; документирование само по себе не делает все 27 core-модулей стабильными.
- Для экспериментальных spatial/анатомических средств явно записать границы и статусы. Новая точка импорта или группировка допустима, если помогает пользователю; переписывать ядро ради красивой структуры не требуется.
- Записать единицы, допустимые интервалы/ошибки и поведение при перемотке. Совместимость относится к объявленному контракту; byte/pixel equality между разными GPU/браузерами не обещается.
- Установить правила версий: несовместимая правка stable-контракта требует major/миграции, совместимое добавление — minor, исправление — patch. Экспериментальные входы отмечаются явно до использования.
- Оставить один короткий путь начала работы, один рабочий пример по каждому поддерживаемому типу задачи и понятный маршрут диагностики. Нынешний ручной registry-edit оцениваем по реальному затруднению автора, автоматизацию заранее не требуем.

### Пакет 2: рамки пилота

Нужна одна полезная законченная задача на будущих стабильных контрактах. Предложенная презентация Curio Motion на 35–45 секунд может быть этой задачей и витриной; отдельный маркетинговый фильм не является условием 1.0. Объём и критерии ограничиваем заранее; при новом рисовании сценарий и стиль фиксируем до работы. Используем существующие механизмы и подходящие принятые элементы; новую функцию добавляем только по конкретному препятствию. Инфографика содержит явно учебные числа либо проверяемые исходные факты. Спорные позы проверяем короткими пробами перед полным фильмом.

Автор выполняет работу; независимый критик проверяет конкретные кадры и переходы; архитектор решает общие проблемы; математик подключается по необходимости. Владелец принимает рисунок и итоговый фильм со звуком. При отсутствии у агента слуха/непрерывного просмотра соответствующая приёмка остаётся за владельцем; автоматический PASS её не заменяет.

Если пригодный результат прежней независимой задачи сохраняет все затронутые входы/контракты, его доказательства можно использовать повторно с явной привязкой. Дополнительная коллекция демонстраций не обязательна.

### Пакет 3: что именно автоматизируем

- Сборка из явного списка публикуемых файлов с исключением локальных цельных референсов, `.env`, Git, зависимостей, кешей, промежуточных outputs/QA и симлинков вне проекта.
- Проверка известных credential-паттернов в импортированном provenance, подготовленной поставке, публикуемом Git-дереве и новых отправляемых коммитах до публикации. Право/атрибуция/лицензионный текст источника сохраняются; очистка HTML явно записывается. Используем штатную защиту GitHub, не обходя её. Такая проверка не обещает обнаружить любой возможный секрет.
- Проверка общего MANIFEST и всех вложенных checksum после изменения source-page evidence; именно устаревшие courier sums уже однажды остановили передачу.
- Явная сверка Git/tag→ZIP: все различия перечислены и разрешены, остальные байты совпадают; источники рендера и зависимости имеют одну привязку. Изменение кандидата после заморозки отменяет связанные результаты до адресной перепроверки.
- Один manifest/версия/состав на конкретный кандидат, проверка установленных зависимостей и прав перед передачей. Исторические принятые архивы не переписываются.
- Регрессионные проверки добавляются для действительно найденного дефекта; дублировать исходную формулу тестом и наращивать число тестов как цель не требуется.

Полная матрица пакета4 выполнена на его замороженном кандидате. Если пакет5 меняет только root version/документы, её browser/API/motion/audio/независимый маршрут могут переноситься на RC только после точного сравнения source/scripts/assets и lockfile с исключением лишь корневой версии. Изменённый image-export-v2 SHA записывается новым; старые receipts не переписываются. Сам RC получает собственные чистые установки/check по маршрутам Git/minimum и ZIP/LTS (перекрёстные пары stage4 переносятся по идентичности), Git→ZIP/history и независимую сверку; один полный официальный RC-экспорт прямо проверяет новый source fingerprint. Если меняются код, зависимости или материалы, адресно повторяем затронутые и зависимые гейты. Только новый сбой или обоснованное сомнение требует расширения. Новая художественная приёмка неизменного принятого фильма из-за текста/версии не выдумывается.

### Блокеры 1.0

- Документированный поддерживаемый маршрут установки/просмотра/экспорта не работает без ручного тайного обхода, падает или теряет файлы.
- Поддерживаемый stable-контракт нарушается; неверные данные дают NaN/сломанный кадр вместо оговорённого поведения.
- В новых принимаемых примерах остаётся согласованный обязательный дефект анатомии/контакта/слоя/данных/звука. Исторические скрытые версии не приравниваются к текущим примерам.
- В распространяемой поставке есть известный действующий credential/приватный вход, неверная контрольная сумма, отсутствующая обязательная атрибуция или неразрешённое происхождение нового материала.
- Новый автор не может закончить проверяемую задачу по инструкции; обход известен только архитектору.
- Заявленная поддержка/совместимость шире подтверждённой; есть незакрытый критичный дефект или обязательный пункт остался OPEN.

Косметические пожелания и новые возможности сохраняются отдельно. Проверка крайних пропорций персонажа становится блокером только в пределах заявленного/поддерживаемого диапазона; переносить неподтверждённый диапазон в обещания 1.0 нельзя.

## Решение о публикации

Условия для решения: пакеты 1–4 закрыты; RC имеет точный commit/архив/manifest; обязательные пункты PASS, ограничения названы; владелец принял результат выбранной рабочей задачи, включая звук, когда он есть, и согласен с объёмом стабильности. После этого готовим предложение публиковать 1.0. Для выбранной рабочей задачи допускается подтверждённое повторное использование прежней приёмки при неизменных входах; новый презентационный фильм не обязателен. После отдельно разрешённой публикации проверяем публичный статус/тег, серверные digest и скачанный release ZIP против замороженного SHA; до этого этап проверки распространения остаётся открытым.
