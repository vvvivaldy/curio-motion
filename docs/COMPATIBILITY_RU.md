# Совместимость и переход с 0.2 к 1.0

Этот документ фиксирует правила1.x. Текущая версия исходников — `1.0.0`; фактическая публикация подтверждается внешней квитанцией выпуска. [Реестр API](API_STABILITY.json) и [точные контракты](API_STABILITY.md) задают ограниченный объём обязательств, а не замораживают всё содержимое `src`.

| Изменение после 1.0 | Правило |
| --- | --- |
| Удаление/перенос stable имени, несовместимая сигнатура, изменение единиц, порядка координат, конца интервала или обещанного lifecycle | Major, описание причины и маршрут миграции. Сохранённый совместимый старый путь может служить переходом. |
| Добавление необязательного параметра/имени/команды с прежним поведением старого вызова | Minor; проверяем совместимость прежнего потребителя. |
| Исправление нарушения документированного stable контракта | Patch; воспроизводимый регрессионный тест. Визуальное влияние на существующие сцены описываем и проверяем отдельно. |
| Экспериментальный helper | Может измениться в minor с записью затронутых импортов/входов и способом перехода. Закрепляйте commit/lockfile. Не смешивать experimental изменение с незаявленной поломкой stable. |
| Внутренний код, диагностический JSON, лог, структура примера | Самостоятельной гарантии нет; инструкции и включённые сцены должны работать на объявленной версии. |
| Обновление зависимости или минимальной среды | Проверка совместимости и заметка в changelog; ужесточение опубликованного поддерживаемого минимума в 1.x требует major. Лицензии зависимостей сохраняются. |

Промежуточные prerelease/RC могут уточнять границу до 1.0; изменения записываем, не называем их обратной совместимостью без проверки. До выпуска сравниваем контракт с принятым baseline этапа 1, сохраняем пользовательские исходники и явно объясняем отклонения. Deprecation не разрешает незаметное удаление stable входа в minor/patch.

## Что нужно изменить существующему автору сейчас

1. Сохранить свой commit/копию сцены, lockfile и принятый фильм. Распаковать поставку 1.0.0 в отдельную папку, перенести собственные исходники и выполнить `npm ci` по поставленному lockfile; не копировать старый `node_modules`. Публичная 0.2.0-beta.1 и её release ZIP не переписываются этой работой.
2. Сверить свои импорты с [20 stable именами](API_STABILITY.md). Пути остаются прежними: `core/stage`, `core/time`, выбранные `core/spatial`, `core/contacts`, `remotion/create-scene`. Нового npm import/barrel нет.
3. Остальные авторские core helpers можно использовать дальше со статусом experimental; диагностический `core/debug.ts` — internal. При обновлении сверяйте конкретные вызовы и затронутые кадры. Рисунки и `pose` остаются авторским кодом. Legacy `src/stage.ts` привязан к обезьяне, а `src/remotion/Scene.tsx` содержит обёртки конкретных Monkey/Robot/Boar; для новой сцены берите общий factory/scene contract, старые wrappers сейчас не удаляются.
4. Единственное изменение исполнения этапа 1: timeline, у которого `(durationInFrames-1)/fps` переполняется до Infinity, теперь отклоняется `RangeError` до `pose`. Задайте осмысленную конечную частоту/длительность. Обычные существующие timelines сохраняют результат; доказательства регрессии записаны в [журнале](STAGE_1_RU.md).
5. Сначала `npm run check`, при изменении рисунка/движения/bridge — относящиеся `check:port` и официальный `render`. Проверить именно затронутые кадры и звук; хеш подтверждает идентичность, не заменяет приёмку.

`SceneSettings` фиксируются на время жизни stage/компонента. `pose` должен быть чистым; кадр задаётся целым номером, секунды выводятся из fps. Уничтожать stage один раз; прикреплённые Pixi children принадлежат stage. Если раньше вы пользовались неоговорённым NaN, повторным destroy или мутацией settings на ходу, это не поддерживаемый контракт.

Тексты ошибок, checksum/QA receipt schema, браузерный DOM и бинарная идентичность разных браузеров/GPUs не входят в stable обязательства. Не путайте воспроизводимость на зафиксированных входах/среде с обещанием одинакового результата на любой платформе.

## Что изменилось в RC

От проверенного этапом 4 кандидата 0.2.0-beta.1 изменены только версия корневого проекта/lockfile и документы выпуска. Код `src`, скрипты, движок и закреплённый граф зависимостей, звук и фильмы сохраняются.20 stable имён, пути импортов, единицы и lifecycle не расширены и не изменены; изменение текстового `scope` в API-реестре не является новым контрактом. Новая версия меняет image-export-v2 fingerprint по определению: старые receipts остаются историческими, перенос проверок требует отдельной нормализованной сверки версии и всех реальных входов. Точная привязка текущего RC и повторных команд — во внешнем отчёте к ZIP.

Для обычной работы используйте Node 26.13.0 LTS (контрольная версия); Node 22.12.0 сохраняется как проверяемый минимум совместимости. Официальный объём — macOS arm64 с названным Chrome; Linux/Windows этого RC не проверены. Переход на1.0 не превращает экспериментальные helpers или готовые рисунки в автоматическую анатомию для произвольных пропорций.

## Продвижение принятого RC в1.0.0

Владелец принял точный 1.0.0-rc.1 (commit 16402397, ZIP 5bb616d2…). Для 1.0.0 меняются версия корневого проекта/lockfile и документы выпуска; реальные source/scripts/dependencies/media сохраняются. Гейты переносятся только по точной нормализованной привязке. Новый fingerprint, fresh stable ZIP check и publication/downloaded checks фиксируются во внешнем отчёте. Прежние RC receipts/архив не переписаны и не выдаются за текущие команды.
