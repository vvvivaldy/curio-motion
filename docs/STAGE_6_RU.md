# Этап 6: выпуск 1.0 и проверка распространения

Это операционный следующий шаг после принятого владельцем RC, а не дополнительная квота функций или новых фильмов. Первоначальный план содержал пять пакетов подготовки; публикация и проверка публичного результата были отдельным решением. Пользователь разрешил: «Да, публикуй стабильную1.0».

| Задача | Условие PASS |
| --- | --- |
| 1. Приёмка/разрешение | Принят exact RC, зафиксировано отдельное разрешение стабильной публикации |
| 2. Версия/документы |1.0.0, совместимость/права и статус исходного снимка согласованы; ранние receipts сохранены |
| 3. Локальный stable | Новый commit и воспроизводимый ZIP, exact RC→stable binding, source/history/checksum/provenance gates |
| 4. Проверка | Один cold ZIP npmci/check и официальный export, независимая сверка; прежние gates перенесены только по идентичности |
| 5. GitHub | Реальный main/tag/release и versioned assets; снимок до публикации не выдан за её результат |
| 6. Public download | Скачан versioned ZIP, digest/SHA/CRC/source совпали с финальным freeze, факт проверен независимо |

Этот документ заморожен до загрузки; фактический прогресс и идентичности находятся во внешних `RELEASE_VERIFICATION_RU.md` / `RELEASE_PUBLIC_VERIFICATION.json`. Пока соответствующий remote/download gate не выполнен, он OPEN. Техническая готовность сама по себе не считается публикацией.

Merge может создать новый OID. Испытанный source commit и публичный merge/tag не приравниваются по названию: сравнивается дерево, финальный PACKAGE_SOURCE указывает фактический tag commit, и обе generated ZIP-разницы проверяются отдельно. Публикуемый asset соответствует `--ref` именно этого commit; GitHub auto source.zip не является его заменой.

Официальный scope остаётся macOS arm64, без Docker/новых VM. Linux browser/export и Windows не получают PASS из удачного CI build. Временные установки удаляются после сохранения доказательств; принятые фильмы/RC/беты и исходники пользователя не переписываются.
